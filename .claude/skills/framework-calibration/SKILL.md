# Framework Calibration — Backtest-Driven Iterative Improvement

## Overview

This skill turns a framework's track record into a calibrated upgrade. It reads every prior report a framework produced, grades what it predicted against what actually happened, diagnoses where the framework's parameters mislead, **adversarially refutes every proposed change** (so overfit/dangerous tunes are killed before they ship), then **auto-applies the survivors** to the framework's `SKILL.md` with a dated revision log, and saves + commits an authoritative retrospective. From the second run onward it also grades the previous calibration itself — every adopted tune's expected effect is a prediction, and it gets the same merciless out-of-sample grading as the framework's own calls.

It is the meta-framework: *Fallen Knives* and *Flying Rocket* analyze markets; **this** analyzes *them*.

**Operating mode (fixed for this workspace):**
- **Scope:** general — point it at any framework's `SKILL.md` + that framework's reports.
- **Apply mode:** **auto-apply** every adversarially-survived tune (with revision-log entry + commit), then report. No per-tune confirmation gate — but the standing guardrails below are hard vetoes that auto-apply may never cross.
- **Depth:** every run launches the multi-agent adversarial `Workflow` when it is available; when it is not, the degraded procedure below preserves the same coverage guarantees. (A skill instructing `Workflow` is itself the user opt-in.)

**Run mode — declare one explicitly, every run:**
- **`full`** — the default. Entire corpus window since the last calibration, mandatory prior-tune re-validation, all four dimensions. May skip nothing without logging it as a coverage gap (dropped report/series/tune), never as a scope decision.
- **`scoped`** — a named subset (e.g., "test these three blind spots," a single dimension, a single asset). Must declare `scopeItems` (what it covers) and `scopeSkipped` (what it does not — most commonly prior-tune re-validation) *before* running, and the ledger line must carry both. A scoped run is not a cheaper `full` run wearing a smaller corpus; it is a different, narrower claim, and the memo must say so in its own section, not bury it in a caveat.
- **`meta`** — see "Calibrating the calibrator" below; no market backtest at all.

2026-08-05b ran `scoped` (three named §9.2 blind spots) without a place in the skill to declare that — prior-tune re-validation was silently skipped and only surfaced in the memo's prose. The three modes above exist so that is a declared choice next time, not an improvisation.

## Inputs — resolve these before running

All five deterministic tools below feed the workflow via its `args` object (`Workflow({ script, args })`) — the same pattern `~/.claude/workflows/poker-hand-analysis.js` uses. The template script itself has no filesystem access; it only receives what `args` carries. There is no more hand-typed `REPORT_FILES` array or hand-copied `PRIOR_CALIBRATIONS` block — both are tool output, read once and passed through.

1. **Target framework(s).** Which `SKILL.md` is being calibrated (default: infer from the user's words — "fallen knives" → `fallen-knives-analytics`, "rocket"/"short" → `flying-rocket-analytics`; if they say "the strategy" / "our predictions" and both have reports, calibrate the one with the richest series and note the other).
2. **Prior adjudications.** Run `node tools/calib-registry.mjs list --verdict rejected --json` (and `--verdict withheld`) — this is `args.priorRejections`, and it replaces the agent that used to re-derive the rejection list from prose memos every run. Also read `reports/calibration_ledger.md` for `PRIOR_CALIBRATIONS` (`{retro, date, summary}` per entry — still small enough to read by hand; leave `[]` on a first run) and the target SKILL's `## Framework Revision Log`.
3. **Report corpus.** `git fetch origin` first (Hard Rule 7), then run `node tools/calib-corpus.mjs --since <last-calibration-date> --framework <fallen_knives|flying_rocket> --out .calib-run/<date>`. Its `corpus.json` `.reports` array is `args.corpus` verbatim, and its `--out` directory (holding one `.slice.md` + `.digest.json` per report, machine block and Verified-Live-Data section already stripped) is `args.corpusDir`. **Default window: reports since the last calibration** (the ledger's latest entry) — earlier reports were already graded, and a clean window keeps each calibration an honest out-of-sample test of the prior tunes. It is also the primary cost control: extraction is the workflow's linear term, and re-extracting already-graded reports is pure waste. Pull in older reports only for still-open positions, for prior predictions graded `untested`, or when the user asks for a full-history re-run. Retrospectives and the ledger itself are excluded structurally (their filenames don't match `<asset>_<framework>_YYYYMMDD_HHMM.md`), not by an exclude-list. More reports = more grading power; a single report is too thin — say so. Check the tool's manifest: a `verified_data_section_not_matched` or `byte_reconciliation` warning means some reports passed through less sliced than usual — harmless to coverage, just less of a cost win.
4. **Ground-truth anchors.** Fetch **live** current price / sentiment / key levels for each asset in the corpus (Hard Rule 1 — live data non-negotiable; the workflow script cannot fetch network itself). This is `args.anchors`.
5. **Realized P&L.** Run `node tools/position.mjs all --json` (Hard Rule 8) — this is `args.position`, and it is now a **mandatory** input per Principle 6: deployment-quality and capital-deployment grading must weigh actual fills/round-trips/win-rate over narrated intent where the ledger covers the asset. Read `.band` before any figure — EXPIRED or missing routes to an explicit "no realized evidence" statement in the grade, never an inferred zero, and never blocks the run (Hard Rule 4's cold-start default governs the absence, same as everywhere else in this workspace).
6. **Companion framework.** If calibrating a long framework that has an inverse (Fallen Knives ⇄ Flying Rocket), the cross-validation dimension must check both.
7. **Toolchain sanity.** Run `node tools/selftest.mjs` before launching the workflow — the frameworks' reports are now built on `tools/` computations, and a broken toolchain invalidates every downstream number. Reports from Jul 2026 on end with a ` ```json machine ` block (schema `report-machine/1`): `calib-corpus.mjs` already projects it into each report's `.digest.json`, so extraction agents never read the raw block; `node tools/lint-report.mjs <report> --legacy` can spot-check any report's arithmetic during grading.

## The pipeline (5 phases — `backtest-workflow.template.js`)

A generalized, runnable workflow script ships alongside this file: **`backtest-workflow.template.js`**. It has no filesystem access of its own — everything arrives via `args`, built from the deterministic tools in Inputs #2–5 above, exactly the way `~/.claude/workflows/poker-hand-analysis.js` takes a pre-parsed hand as `args` rather than reading a screenshot itself. Each run: `Workflow({ script: <this file>, args: { corpus, corpusDir, priorRejections, priorCalibrations, anchors, position, skillDir, targetSkills, mode, scopeItems, scopeSkipped, knobs } })`. Phases:

1. **Extract** — one agent per chronological same-series **chunk of ~6 reports** (`EXTRACT_CHUNK`, hard ceiling 8), reading the **pre-sliced** `.slice.md` files (machine block + Verified-Live-Data section already stripped by `calib-corpus.mjs`) with each report's `.digest.json` supplied inline → one structured extraction *per report* covering the PROSE only: probability scenarios (only where the digest lacks them — pre-epoch reports), `IF→THEN` Pattern conditionals, falsifiable claims, declined discretionary actions. Numeric fields (score, gates, EV, deployment/stop state) are **joined in code from the digest**, never re-derived by the agent — the same code-side join identity fields already got in v2. Barrier (grading needs the whole series). Failed chunks are logged as uncovered, not silently dropped.
2. **Grade** — one agent per **framework × asset series** (a long and a short framework on the same asset are different track records) reconstructs the realized path and marks every prediction `correct / partial / wrong / untested` with evidence; quantifies EV-calibration bias, deployment quality (was capital locked out of cheaper zones? cross-checked against the realized-P&L ledger where it covers the asset), stop near-misses, and a `realized_pnl_note` — what the ledger actually shows, or an explicit "no realized evidence" statement, never an inferred zero; independently re-verifies the most load-bearing path numbers because reports occasionally carry invented figures. Plus a cross-validation grader (companion-framework inverse-consistency). Plus, on a `full`-mode run from the second calibration on, a **prior-tune re-validator**: every tune the last calibration adopted is graded `validated / harmful / not_exercised / indeterminate` on the post-calibration path and prior `untested` predictions are re-resolved — the rejection list itself no longer needs re-deriving here, it arrived as `args.priorRejections` from `calib-registry.mjs`.
3. **Diagnose** — one agent per **framework × merged dimension** (4: scoring-and-gates, capital-deployment [pyramid + stops], forecast-calibration [probability/EV + voice/judgment], data-integrity [data-quality + cross-asset + cross-framework]) → flaws-with-evidence + proposed tunes (exact before→after); fewer, stronger tunes are explicitly preferred — every proposal costs an adversarial panel downstream. Diagnosers see the prior adjudications: re-proposing a rejected tune requires naming it and citing new out-of-sample evidence; reversing an adopted one requires a `harmful` re-validation grade. **Any dimension that returns zero tunes gets a NULL ADVERSARY pass** — an independent agent briefed specifically to attack that null before it is trusted (see Principle 7). A tune survives triage/skeptics normally either way; the null adversary only decides whether a zero gets a second, harder look.
4. **Verify (adversarial)** — first a **triage** agent clusters near-duplicate tunes by name (runs only when >8 proposed; code rebuilds the kept list from the originals, so triage never rewrites tune text and can drop nothing silently). Then **skeptic panels, batched**: ~5 tunes per skeptic agent (`VERIFY_CHUNK`), per-tune verdicts, default-to-refute — except tunes from the **capital-deployment dimension, which always get per-tune solo panels** (they move money; batching scrutiny there is a false economy). Every verdict also names **toolchain coupling** — does the tune move a band/threshold/cap that `tools/lib.mjs` mirrors, and if so which symbol. `SKEPTICS_PER_TUNE` (default 1; 2–3 on a thorough audit, each pass taking a different lens: overfit/counterfactual, guardrail-collision, evidence-verification) multiplies only this phase. Votes merge **strictest-wins** (any reject vote rejects; a tune with no surviving verdict is *unadjudicated*, which is not an adoption). Verdict: `adopt / adopt_with_modification / reject`. **Plus an applied-edits audit** of the *previous* calibration's edits in the live SKILLs (incl. whether their `lib.mjs` pairing landed), and a **pre-apply audit** that takes the whole adopted set together and checks mutual consistency, reachability, throttle, decoupling, threshold crossings, scope, and toolchain coupling before anything ships — its `final_text` is the form that gets applied, and `toolchain_edit_required` says what must land alongside it.
5. **Synthesize** — the authoritative memo: run scope (mode + what was covered/skipped), prior-calibration re-validation, realized-path scorecard (incl. realized P&L), prediction-accuracy analysis, ranked structural flaws (flagging null-adversary-sourced ones), the **verified tuning set** (adopted vs rejected, with *why the rejections matter*, plus toolchain edits required), remaining edits, coverage disclosure (dropped reports, unadjudicated tunes), and an explicit "what to preserve."

**Cost is bounded structurally, never by skipping coverage.** The corpus window (since the last calibration — input #3) bounds the report count; the corpus tool's slicing bounds each report's bytes (machine block + Verified-Live-Data section stripped — measured ~32% reduction on the 2026-07-04→2026-08-05 FK window, more on machine-block-heavy reports); extraction chunking bounds the linear term (~R/6 agents, not R); merged dimensions and batched panels bound the rest. Approximate agent count: `Σceil(series/6) + (series+2) + 4×frameworks + up to 4×frameworks null-adversary (only zero-tune dimensions) + 1 triage + skeptics×(ceil(tunes/5) + capital_tunes) + 3` — a 90-report / 3-series month runs ~30 agents where the v1 design ran ~125, on roughly two-thirds the extraction bytes. "Exhaustive" means every report extracted, every prediction graded, every tune adversarially refuted, every unanimous null attacked once — it has never meant one agent per datum. A "thorough audit" request widens `SKEPTICS_PER_TUNE` to 2–3 (multiplies only the Verify phase).

## When `Workflow` is unavailable

The packaged `Workflow` tool has been unavailable in two of the last three real invocations of this skill (2026-08-05, 2026-08-05b) — improvised each time, with no documented fallback, on 2026-08-05b that meant **Extract and Grade never ran as separate passes over the full 49-report corpus**. This is the standing procedure for that case, not a template of last resort:

1. **Preserve the phase barrier.** Extract must still complete, chunked, before Grade begins; Grade before Diagnose; Diagnose (+ null adversary) before Verify; Verify before Synthesize. Running phases out of order or collapsing them (as 2026-08-05b's per-item diagnosers did, extracting and grading their own evidence inline) is the exact failure this section exists to prevent.
2. **Preserve the code-side identity join.** Extraction output must still be joined to `{file, asset, framework, date}` deterministically — from `args.corpus`, never trusted from agent output.
3. **Preserve strictest-wins vote merging and solo panels for capital-deployment tunes.** These are not template conveniences; they are the actual adversarial guarantee. A single agent adjudicating its own proposal is not a skeptic panel.
4. **Preserve the null adversary.** A dimension (or an entire run) landing on zero tunes gets one independent attack against that null before it is trusted — run it as a separate agent call, not folded into the same diagnoser that produced the null.
5. **Log the degraded mode explicitly.** The ledger line's headline must state `Workflow unavailable — degraded procedure` and name anything the substitution cost (a merged phase, a skipped independent pass, fewer skeptic lenses). This is coverage disclosure, the same discipline as a dropped report or an unadjudicated tune — never silent.

## Adjudication → auto-apply policy

After the workflow returns, **apply every tune whose panel verdict is `adopt` or `adopt_with_modification` AND whose pre-apply audit says `apply_ok`** — using the audit's **`final_text`**, not the original proposal (that is the adjudicated form). **Never apply a `reject`.** A tune returned in `unadjudicated_tunes` (its skeptic panel died mid-run) is **not** an adoption: list it in the memo as uncovered and re-run its panel before it may ever be applied. Then:

1. For each adopted tune, **Read the target SKILL, locate the exact text, and Edit** it to the adjudicated form. Map every before→after precisely — these are surgical edits to a live framework.
2. **Toolchain coupling — apply together or not at all.** If the pre-apply audit's `toolchain_edit_required` names a `tools/lib.mjs` symbol for a tune, that `lib.mjs` edit + its `selftest.mjs` vector land in the **same commit** as the SKILL edit — never the SKILL edit alone, never a follow-up commit. A tune with an unaddressed `toolchain_edit_required` is not applied this run; log it as withheld, same as a guardrail trip.
3. **Run a validation pass** (grep): no duplicate list numbering, no broken cross-references, no stale text left behind (old thresholds, removed multipliers), no operator-precedence ambiguity in compound unlock clauses. Fix any defect the audit flagged in a prior calibration's edits.
4. **Run `node tools/selftest.mjs`, then `node tools/lint-report.mjs` on the target framework's most recent report.** A calibration that changes a rubric and doesn't re-verify the toolchain against it is exactly how a SKILL/`lib.mjs` desync would first surface — catch it before the commit, not on the next report.
5. **Add a dated `## Framework Revision Log` entry** (create the section if absent) summarizing: each applied tune (before→after, one line), the rejected tunes **with why** (the rejections are half the value — they document what *not* to do), and the standing N=1 caveat.
6. **Append every adopted/rejected/withheld/unadjudicated tune to `reports/calibration-registry.json`** via `node tools/calib-registry.mjs append <payload.json>` — this is what makes the NEXT run's `args.priorRejections` correct without an agent re-deriving it from this run's prose.
7. **Mirror to a companion framework only with the asymmetry filter** below.

## Standing guardrails — hard vetoes that auto-apply may NEVER cross

Even a tune the skeptics passed is **rejected at apply-time** if it would:

- **Relax short-side discipline** (Flying Rocket): no deep-greed/override-style loosening, no stop loosening, no gate softening. Per Hard Rule 6 the short side only ever gets *tightening* or direction-neutral mirrors from the long side; when mirroring a long-side tune, apply it **only if it cannot make a short easier**, otherwise withhold it and log the withholding as deliberate. **Amended 2026-07-27:** score *thresholds* are no longer part of this veto — the owner re-sited the asymmetry tax onto risk control, and the 11/13/15/19 lines are now evidence-driven and revisable in either direction. Everything else in this bullet stands unchanged, and seven things are now permanently out of scope for any tune: a stop, a time stop, a size cap, the S6 ratchet, a cover trigger, the carry veto, and the Channel B funding veto gate.
- **Weaken the FR discretion tax or the Channel B budget** (added 2026-07-27) — the short-side loosenings (Channel B's existence, the cut 11/13/15 lines, the 1A gate floor of 3, the S1 ±2 term, the S2 conviction path) were licensed *only* against the S5 tax (half size, ≤6% stop, 14-day clock, 20% book cap, no Phase 3), the S6 ratchet, and Channel B's own budget (30% of book, no Phase 3, 21/28-day clocks, gate-8 veto). A tune may tighten any of these. A tune that loosens one — a wider analyst stop, a longer clock, a higher cap, a Channel B Phase 3, an exception to the ratchet, or a waiver of the funding veto — is **rejected at apply-time even if every skeptic passed it**. Loosening the entry side further while the risk side stands is a normal tune, judged normally. What is vetoed is unbundling the pair. Note the asymmetry with FK's D6: **S6 has no exception at all**, and adding one is itself a prohibited loosening.
- **Loosen a capital guardrail into a falling knife** — front-load size at shallow drawdown, deploy more on a thin score, credit *failed* trend gates toward an unlock, or remove a stop entirely. (These were the dominant rejection reasons in the Jun 2026 calibration.)
- **Damage a documented "what to preserve" behavior** — the retrospective's preserve-list (e.g., the framework's correct *refusals* to deploy, conservative sizing, "honor the close" stops). A tune that improves one metric by breaking a survival behavior is rejected.
- **Break its own central mechanism** — e.g., a score penalty that knocks the score below a deployment-override threshold at the lows, disarming the override exactly when it should fire. Check every score-touching tune against the unlock thresholds it could cross.
- **Weaken the discretion tax** (Fallen Knives, added 2026-07-27) — the Analyst Discretion Layer's entry loosenings (D1 ±2 term, D2 conviction path, cut 1A/1B unlock lines, D4 probability freedom) were licensed *only* against the D5 hard price-only stop and the D6 one-way ratchet. A tune may tighten either; a tune that loosens **D5** (deeper than 15% below fill, a score condition, second-close patience, exemption for a channel, a higher discretionary capital cap) or **D6** (any new widening exception) is rejected at apply-time even if the skeptics passed it. Loosening the entry side further while the stop side stands is a normal tune and is judged normally — what is vetoed is unbundling the pair.
- **Cross the edit-surface boundary** — auto-apply may edit the target framework SKILL file(s) only. Workspace Hard Rules (`CLAUDE.md`) are read-only context: a tune that needs one changed (pyramid splits, cross-validation law, short-side asymmetry) is surfaced to the user as a recommendation, never applied.
- **Reverse a prior calibration's adopted tune without out-of-sample evidence of harm.** Reversal is a tune like any other, but its evidence bar is the prior-tune re-validator grading it `harmful` on the post-calibration path. Re-arguing the original debate on the same evidence is thrash, not calibration — oscillating parameters are worse than imperfect stable ones.
- **Ship a SKILL edit desynced from the toolchain it mirrors** (added 2026-08) — CLAUDE.md's Deterministic Tooling section already requires this: a band/threshold/cap change in a SKILL that `tools/lib.mjs` also encodes must land with the matching `lib.mjs` + `selftest.mjs` edit in the **same commit**. A tune whose pre-apply `toolchain_edit_required` isn't addressed this run is withheld, not applied with the coupling deferred — a SKILL that says one threshold and a `lib.mjs` that computes another is worse than not having tuned at all, because every report after it silently trusts the wrong one.

If an otherwise-adopted tune trips a guardrail, **do not apply it**; record it in the revision log under "withheld at apply-time (guardrail)" with the reason.

## Reachability & internal-consistency checks (apply-time, mandatory)

The Jun 2026 pass shipped a Deep-Value Override that was **mathematically unreachable** (its trigger sat below the deepest realized price, so it never fired). The workflow's pre-apply audit now runs these checks with full backtest context *before* adjudication ships; re-verify them at apply-time anyway — they are cheap, and they are exactly the checks that once failed silently:

- **Reachability:** would the new trigger have fired somewhere on the realized path it's meant to handle? If not, it's decorative — re-anchor it (e.g., to a trailing low / close, not just report-time spot) until it would.
- **Throttle:** any rule that *adds* exposure must have a cap and an interaction rule with any opposing modifier, so it can't chain-runaway through an uninterrupted cascade.
- **Decoupling:** a deploy-trigger and a stop-trigger must never key off the same number.
- **Denominator/N/A:** if gates can be N/A for some asset class (e.g., PoW-only signals on PoS assets), reduce the denominator — never leave an unfillable gate inflating the count.

## Output & git (Hard Rule 7 + Auto-push)

- Save the memo to `reports/strategy_retrospective_[YYYYMMDD].md` (or `[framework]_calibration_[YYYYMMDD].md` for a single-framework run).
- Append a one-line entry to **`reports/calibration_ledger.md`** (create if absent): date · framework(s) · run mode (`full`/`scoped`/`meta`, + `Workflow unavailable — degraded procedure` if applicable) · corpus window · #adopted/#rejected (+#withheld/#unadjudicated if any) · prior-tune re-validation tally (validated/harmful/not-exercised) · headline change · "N=1 — re-validate after next full cycle." This ledger is the running tuning history across calibrations **and the input to the next run's `args.priorCalibrations`** — keep it accurate.
- **Commit + push** the changed SKILL(s) + retrospective + ledger in one commit (message: what was calibrated, top adopted/rejected, evidence window). Do not sweep unrelated working-tree changes into it.
- Post a ≤8-line summary: predictions-right-vs-wrong tally, the 1–2 highest-leverage tunes applied, the most important *rejection*, and the N=1 caveat.

## Principles

1. **The track record is the test set.** A framework's own prior reports are a closed, honest dataset — its later reports + live data are the ground truth for its earlier predictions. Grade against them mercilessly.
2. **Rejections are as valuable as adoptions.** Most "improvements" that touch a score or loosen a gate make the realized outcome worse. Document why each rejected tune was rejected so the next calibration doesn't re-propose it.
3. **Preserve what survived.** Separate *forecasting honesty* (fix freely) from *risk discipline* (the actual edge — touch only to harden). The frameworks usually survive *because* they doubted their forecasts enough to stay disciplined; make that doubt structural without relaxing the discipline.
4. **Every calibration is N=1.** Tunes fit to one regime are provisional. Strip the most path-fitted parameters, prefer direction-of-effect over point-precision, and flag thresholds for re-validation after the next full cycle.
5. **Asymmetric humility carries over.** When a long-side fix has a short-side mirror, the mirror is applied only if it can't make the short easier. The withholding is itself a logged decision.
6. **Grade the analyst's discretion as a channel** *(Fallen Knives, added 2026-07-27)* — every FK report from 2026-07-27 carries a **Discretion Ledger** (§9) whose entries are testable predictions: the D1 term, D2 conviction-path unlocks, D4 probability deviations, and the discretionary actions **declined**. Grade each one exactly as an adopted tune is graded — `validated / harmful / not_exercised / indeterminate` — and answer the counterfactual explicitly: *did the cut 1A/1B unlock lines and the conviction path buy better entries than the ≥10/≥13 bars would have, net of D5 stop-outs?* Report per-channel hit rates and realized P&L. A channel that grades harmful is tightened or withdrawn; the layer shipped N=0 and its first calibration is its first real evidence.

7. **Grade Channel B against its own falsifiers** *(Flying Rocket, added 2026-07-27)* — the bear-continuation channel shipped with four named falsifiers (F1–F4 in `reports/fr_eth_fall_capture_backtest_20260727.md`) and a parameter set read off six ETH events. Grade each falsifier explicitly, and answer the two counterfactuals the backtest could not: *(a)* did Channel B entries beat standing aside, **net of funding, borrow and slippage** — none of which the price-only backtest contained; *(b)* did the ≥10%-fall capture rate actually reach the 50% mandate, measured on realised falls rather than on the backtest's estimate? Report the mechanical-vs-S1/S2 split separately, and report **stop-outs followed by the fall proceeding anyway** as its own number — that is F4, and it is the failure mode most likely to be mistaken for bad luck. If capture is met but expectancy is negative, the channel is *not* validated: the mandate was "enter 50% of falls **with risks handled**," and the second clause is the binding one.
8. **Grade the calibrator before the framework.** From the second run on, the first question is "did the last calibration's tunes survive contact?" — adopted tunes graded on whether they fired/bound/helped, rejections checked for vindication, `untested` predictions re-resolved. A calibration loop that never audits itself just accumulates plausible edits; this re-validation is what makes "N=1 — re-validate after next full cycle" an executed step instead of a disclaimer.
9. **Attack a unanimous null before trusting it** *(added 2026-08)* — on 2026-08-05b, three independent diagnosers all returned zero tunes; a fourth, adversarial pass found the one clause that shipped. Had the pipeline accepted the consensus, it would have recorded a false "no defect found" and the report that motivated the run would have gone unaddressed. Every dimension (and every full run) that returns zero tunes now gets one independent adversary briefed specifically to attack that null — not to re-run the same diagnosis, but to try, on purpose, to find what consensus missed. A null that survives a real adversarial attempt is worth trusting; a null nobody tried to break is not evidence of anything.

## Calibrating the calibrator

When the user asks to improve **this skill itself** ("improve the calibration skill", "look into this skill") rather than a market framework: do **not** launch the market backtest. The deliverable is edits to this `SKILL.md` and `backtest-workflow.template.js`, grounded in this skill's own track record — the calibration ledger, the retrospectives, the target SKILLs' revision logs, and any process defects they document (edits that shipped broken, checks that ran too late, corpus/adjudication gaps). Apply the same standards this skill applies to the frameworks: evidence over speculation, preserve what worked, reject speculative complexity, and log the change (a `meta` line in `reports/calibration_ledger.md` + commit).

## Voice

Calm, quantitative, unsentimental — the same allocator voice as the frameworks it calibrates. Lead with the honest verdict (what was right, what was wrong), then the evidence, then the change. Never oversell a tune; always state the uncertainty.
